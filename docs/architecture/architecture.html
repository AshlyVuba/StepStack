1. Overview and implementation status

StepStack is an adaptive digital and financial skills platform for South African learners, built as an offline-first PWA paired with a lightweight Fastify API:

  • A frontend in frontend/: an offline-first Progressive Web App written in plain HTML, CSS and JavaScript with no build step and no third-party runtime libraries. It caches the app shell and pre-translated 11-language static lesson packs (frontend/packs/), runs deterministic client-side grading (typing, spreadsheets including ZAR household budgeting & loan interest, Python, and safe offline SARS eFiling form validation), and keeps all learner data encrypted on the device.
  • A backend in backend/: a lightweight Fastify and TypeScript API (zero live local CPU/GPU LLM inference at runtime) that serves versioned 11-language static lesson packs (GET /v1/lesson-packs/:lang), re-verifies synced submissions deterministically (HyperFormula, Pyodide WebAssembly sandbox, structured SARS form grader), and issues HMAC-SHA-256 cryptographically signed, verifiable portfolios stored in PostgreSQL.

3. Frontend (PWA) architecture

3.2 Startup and screens

main.js calls startApp(), which registers the service worker and asks the vault to initialise. The vault answers one of three ways:

  • new: first run on this device. The setup screen asks whether the device is the learner's own or shared.
  • locked: a shared device that already has data. The unlock screen asks for the passcode.
  • ready: a personal device. The learner goes straight in.

After onboarding, onboarding.js dispatches a stepstack:onboarded event and app.js loads the workspace on demand. Keeping the workspace, grading code and exercise content out of the startup path is what holds the first screen to 12.57 KB gzipped (Section 8).

3.3 Offline-first service worker

sw.js is registered by pwa.js and works as follows:

  • Install: pre-caches 21 entries (the page, scripts, styles, manifest, icons and the landing art) into the cache stepstack-shell-v1. The list is written by hand, and a CI check fails if any shipped file is missing from it.
  • Activate: deletes older caches whose names start with stepstack- and takes control of open pages.
  • Fetch: handles only same-origin GET requests. A cached file is returned immediately and refreshed from the network in the background (stale-while-revalidate), so updates arrive on the next load without bumping a version number. A navigation that is not cached falls back to the cached index.html. An uncached non-navigation request fails when offline instead of returning something wrong.
  • Never touches learner data. Learner data lives encrypted in IndexedDB, not in any cache.

This was verified in headless Chromium: after one visit with the network on, the page was reloaded offline, the offline banner appeared, and a Stage 1 drill was completed.

3.5 Local content and practice grading

The workspace has 3 tiers (digital basics, Excel and office, coding), each with 3 stages: a micro-drill, a guided challenge and a capstone. Interface text and instructions exist in English, isiZulu and Afrikaans, while onboarding offers all 11 languages; a learner who picks another language sees English. Short answers are graded by normalising the text (lower case, no spaces, curly quotes straightened) and matching regular expressions. Capstones are accepted once the answer reaches 20 characters. Because the patterns ship in the browser, this grading is for practice only. Anything that must be trusted, such as a verified portfolio, needs the server-side grading in Section 5.

4. Offline queue and sync engine

The proposal describes an offline sync engine. This section separates what exists from what does not.

4.1 What exists IMPLEMENTED

  • Event capture. The first time a learner completes a stage, workspace.js enqueues an event: {"type":"stage-complete","payload":{"tier":"workplace","stage":0,"exercise":"w1"},"at":"2026-11-26T09:15:00.000Z"}. Re-checking an already completed stage does not enqueue again.
  • Encrypted storage. Each event is encrypted (record name queue) and added to the queue store, so completions are never lost while offline and are unreadable while a shared device is locked.
  • Drain mechanism. flush() sends events oldest first through a registered sender and deletes an event only after the sender succeeds. At the first failure it stops and keeps the rest. It runs when the browser fires its online event, and only while the vault is unlocked.

4.2 What does not exist PLANNED

  • No sender. queue.setSender() is never called, so flush() returns immediately and events stay queued.
  • No network code. The frontend has no HTTP client, no retry or back-off logic, and no learner identity to attach to events.

4.3 Constraints for completing the sync engine PLANNED

These follow from how the two halves are built today and should guide the integration work:

  1. A server-side relay is needed. The backend endpoint that records capstone completion requires a secret x-internal-key and a learner UUID. The key must never ship in browser code, and the browser has no learner UUID because there are no accounts yet. The backend's own README describes an LMS as the caller; no such service is in the repository.
  2. Delivery is at-least-once. Because flush() deletes an event only after success, a lost acknowledgement means the event is sent again. Receivers must tolerate duplicates. The backend's portfolio creation already does: it is idempotent per learner and capstone.
  3. Identifiers do not match. The frontend uses exercise ids such as w1; the backend uses ids such as sum-basic. One side must map to the other.
  4. No endpoint accepts stage events. The backend has capstone completion and grading endpoints, but nothing that stores per-stage progress.

5. Backend services IMPLEMENTED

The backend is one lightweight Fastify 5 process on Node 22, written in TypeScript (512 MB memory cap; zero live local CPU/GPU LLM inference at runtime). app.ts builds the app with its dependencies injected (database repository, static lesson pack store, optional cache, sandbox pool), which is how the tests swap in memory versions. Every app registers helmet security headers, explicit CORS origin checks, a rate limit of 120 requests per minute per IP, and validates each request body with zod.

Configuration (config.ts) is read from the environment and validated at startup. There are deliberately no default secrets: the server refuses to start if PORTFOLIO_SIGNING_KEY (32+ characters), INTERNAL_API_KEY (24+ characters), or DATABASE_URL is missing or weak. Neither ANTHROPIC_API_KEY nor REDIS_URL is required at runtime.

5.1 Deterministic grading & Financial Literacy simulations

Exercises, including their expected answers, live as JSON files in backend/exercises/ (typing, Excel/Financial Literacy, SARS eFiling form simulations, and Python). Clients grade deterministically offline for instant feedback and send exercise IDs + answers upon sync for server verification and cryptographic portfolio signing.

  • Typing is graded in process: Levenshtein edit distance gives accuracy, correct characters divided by 5 per minute gives words per minute, and anything above 250 WPM is rejected as automated input.
  • Excel & Financial Literacy (ZAR) formulas are evaluated by HyperFormula (pure calculation engine, no eval, no I/O). Includes multi-case South African Rand household budgeting (household-budget) and microloan simple interest & repayment (loan-interest) drills so hard-coded numbers fail.
  • Safe Offline SARS eFiling Simulations (POST /v1/grade/form) validate structured beginner tax exercises (sars-registration and sars-irp5-itr12: 10-digit training tax reference format, 13-digit SA ID format, IRP5 source codes 3601/4102/4005 with Rand currency parsing, and password/OTP safety). Marked simulationOnly: true with zero contact to any live government portal.
  • Python runs in a pool of warm, single-use Pyodide (Python on WebAssembly) processes. The next paragraph explains the isolation.

Isolation layers for Python submissions (in the order they apply):

  1. Request limits: code up to 10,000 characters, 20 submissions per minute per IP, and at most 20 requests waiting for a worker (beyond that the API answers 503 busy).
  2. Process isolation: each worker starts with an empty environment (no API keys or database URLs), a 256 MB heap cap, and a 256 KB output cap. It grades exactly one submission and is then killed, so nothing leaks between learners. A replacement is started immediately to keep latency low.
  3. Time box: the parent process sends SIGKILL when the time limit expires (default 1,500 ms, configurable 200 to 1,900 ms), which stops infinite loops and runaway memory.
  4. AST gate: before anything runs, the code is parsed and rejected if it imports outside a 16-module allowlist, reaches for dunder or frame attributes, uses eval, exec, open and similar, or contains async code.
  5. Restricted execution: the code runs with a hand-picked builtins dictionary, allowed modules exposed as plain namespaces of public attributes, print disabled, and a recursion limit of 300. Tests marked hidden report only "Wrong answer on a hidden test".

5.2 Pre-translated 11-language static lesson packs (zero live runtime LLM inference)

StepStack does not run live on-device or live server CPU/GPU LLM inference per learner click. Instead, backend/scripts/build-lesson-packs.ts compiles all master lessons from data/exercises.json ahead of time into versioned, syntax-verified JSON bundles across all 11 official South African languages (en, zu, xh, af, nso, tn, st, ts, ss, ve, nr).

  • Sanitising (sanitize.ts). Input is NFC-normalised, control and invisible characters (used to hide instructions) are stripped, delimiters are removed, and over-long text is rejected rather than truncated.
  • Syntax-lock protection (protect.ts). Code blocks, inline code, Excel formulas (e.g. =SUM(A1:A5), =SUM(B3:B7), =B2*B3*B4), cell references, function names, and Python keywords are locked behind numbered placeholders (⟦n⟧) during compilation and verified afterward with verifySyntaxLock().
  • Deterministic CI builds. When run without an external API key (npm run build:packs), the CLI uses MockBuildLlm so CI stays 100% deterministic; optional --live compilation supports build-time translation via Anthropic Claude.
  • Static offline delivery. Compiled bundles live in backend/lesson-packs/ (served via GET /v1/lesson-packs and GET /v1/lesson-packs/:lang with Cache-Control + ETag) and frontend/packs/. On the learner device, frontend/sw.js caches fetched packs in stepstack-packs-v1 and frontend/src/js/idb.js stores them in IndexedDB (packs store) for 100% offline use.
  • Runtime fail-closed. In production with no live LLM attached, POST /v1/translate resolves known curriculum strings directly from static packs and returns 503 live_inference_disabled for uncompiled text.

5.3 Portfolio issuing and verification

  • Issue. An internal service calls POST /v1/capstones/complete with the secret key (compared in constant time). The row is inserted with ON CONFLICT (learner_id, capstone_id), so repeating the call returns the same portfolio. The response contains a portfolioUrl and a verifyUrl built around a signed token.
  • Token. The token has the form v1.<payload>.<signature>, where the signature is HMAC-SHA-256. The payload holds only an opaque random portfolio id and an issue time, never learner data. A previous signing key can be kept during rotation.
  • Verify. GET /v1/verify/:token is public. A bad signature and an unknown id return the identical 404, so ids cannot be probed. A revoked portfolio returns 410. A valid one returns the display name (an alias, not a legal name), capstone id, issue time and skills, and never the learner id.
  • Revoke. POST /v1/portfolios/:id/revoke sets revoked_at.

The issue response includes a /p/<token> page address, but no route serves that page yet. Only /v1/verify/:token exists.

6.2 Optional cache (backend)

Static 11-language lesson packs are served directly from pre-compiled JSON files (backend/lesson-packs/) with zero Redis requirement at runtime. If REDIS_URL is configured, Redis may still be used for optional build/staging cache entries; otherwise the API runs with an in-memory fallback.

6.3 IndexedDB (frontend)

The database stepstack (version 2) has five stores: meta, keys, data, queue, and packs (holding pre-translated 11-language static JSON lesson packs for 100% offline access).

7. Data flow

7.1 Learner completes a drill, online or offline IMPLEMENTED

  1. The learner types an answer and presses Check. grading.js grades it locally against patterns.
  2. On the first correct answer for a stage, the event is enqueued: encrypted and added to the queue store.
  3. Progress (completed stages and drafts) is encrypted and saved to the data store.
  4. The screen shows feedback and moves the progress bar. No network request is made, whether the device is online or not.

7.2 Journeys that exist only in the backend BACKEND ONLY

  • Grading (Figure 2): client sends an exercise id and answer, the server looks up the expected result, grades it (Python in a sandbox), and returns a verdict and feedback.
  • Translation (Figure 3): the server sanitises, checks the cache, calls the model on a miss, verifies the code survived, caches lesson text, and returns the translation.
  • Portfolio (Figure 4): an internal service issues a signed link; anyone with the link can verify it without logging in.

8. Low-bandwidth optimization strategy

Trade-offs to be aware of

  • Background refresh uses data. The service worker returns cached files instantly but also re-requests each one in the background. On later visits the cost depends on the host sending proper cache headers (so unchanged files answer with a tiny "not modified"). Those headers are not set by this repository.
  • Local grading is a trade for offline use. It saves bandwidth and works offline, but it can be inspected in the browser, so it is only for practice (Section 3.5).
